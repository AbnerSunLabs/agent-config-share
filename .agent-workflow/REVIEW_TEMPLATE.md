## 3. Finding 格式

每条 Finding 使用以下结构：

```markdown
### [P1][high] F-001：一句话标题

- 位置：`path/to/file.ts:42`
- 类别：correctness
- 影响：说明真实用户、数据、接口或运行时影响。
- 证据：描述可执行路径、输入、状态或失败结果。
- 建议：给出最小修复方向，不替实现者完成设计。
```

优先级：

- P0：安全漏洞、数据丢失或生产事故风险，必须修复。
- P1：逻辑错误、验收失败或破坏性回归，必须修复。
- P2：重要质量问题，需要修复或明确接受理由。
- P3：非阻断优化建议。

置信度：

- `high`：代码路径和影响可以直接证明或复现。
- `medium`：证据充分，但依赖一个明确假设。
- `low`：需要额外运行时或业务证据；不得单独作为 P0/P1 阻断结论。

## 5. 基础检查清单

### Correctness

- [ ] 关键状态和数据流符合设计。
- [ ] 输入边界、空值、重复调用和失败路径处理正确。
- [ ] 异步、并发、缓存和资源生命周期不存在明显竞态或泄漏。
- [ ] 不存在只修补表象而保留根因的问题。

### Acceptance

- [ ] 每条验收条件都有对应实现。
- [ ] 非目标没有被静默纳入范围。
- [ ] 行为与执行授权包一致。

### Testing

- [ ] 行为变化有有效测试或等效证据。
- [ ] Bug 修复包含能防止原问题复发的回归检查。
- [ ] 测试验证行为而非实现细节。
- [ ] 关键失败和边界场景已覆盖。
- [ ] 测试结果来自真实执行。

### Error handling

- [ ] 异常不会被吞掉或伪装成成功。
- [ ] 错误信息对调用者和排障有用。
- [ ] 超时、重试、降级和清理逻辑符合风险。

### Compatibility

- [ ] 公共 API、配置、数据和协议变化已识别。
- [ ] 迁移和回滚路径可行。
- [ ] 不会破坏未修改的调用方或旧数据。

### Security

- [ ] 无硬编码凭证或敏感数据泄露。
- [ ] 输入、输出、权限和信任边界清晰。
- [ ] 注入、越权、路径穿越、SSRF、XSS 等适用风险已检查。
- [ ] 日志和错误不会暴露秘密信息。

### Maintainability

- [ ] 修改遵循现有架构和命名。
- [ ] 没有不必要抽象、重复路径和过度设计。
- [ ] 复杂逻辑被拆分为可独立理解和测试的单元。
- [ ] 注释解释 Why，不重复 What。

## 6. Profile 扩展检查

### Web

- [ ] 键盘、焦点、语义和可访问性。
- [ ] 响应式、加载、空态、错误态和视觉回归。
- [ ] 浏览器真实交互而非仅静态代码判断。

### API

- [ ] 请求响应 schema、错误码和幂等。
- [ ] 认证、授权、限流和向后兼容。

### Database

- [ ] 事务、锁、索引、约束和数据完整性。
- [ ] 迁移可观察、可回滚或有安全前滚策略。

### Agent

- [ ] 上下文构建、工具权限和 Prompt 注入边界。
