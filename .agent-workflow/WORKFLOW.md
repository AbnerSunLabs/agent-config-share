# 跨 Agent 个人研发工作流

> 本文件是研发流程的唯一事实源。任何 Agent、Skill、插件或适配文件都不得覆盖这里定义的阶段、授权边界和完成标准。  
> 各宿主「如何实现同一职责」见同目录 `CAPABILITIES.md`；宿主专属插件名不得写入本文件。

## 1. 启动顺序

开始任何非琐碎开发任务前，执行者必须按顺序读取：

1. `.agent-workflow/WORKFLOW.md`
2. `.agent-workflow/PROJECT.md`
3. 当前任务文件 `.agent-workflow/tasks/<task-id>.md`
4. 项目自身声明的架构、测试和贡献文档

需要对照当前宿主用什么工具落地时，再读 `.agent-workflow/CAPABILITIES.md`（非每次任务强制全文精读）。

如果 `PROJECT.md` 或任务文件不存在，先基于对应模板创建；不得依赖聊天上下文代替持久化任务事实。

**默认启动：** 入口文件已对齐的仓库中，收到非琐碎开发任务即按本文件执行（探索 → 规划设计写入任务文件 → `awaiting_approval` → 停止改业务源码）；用户无需重复粘贴启动话术。批准可用简短表述（如「批准，L2」）。

## 1.1 冲突优先级

规则冲突时按以下顺序（高 → 低）：

1. 宿主安全审批与环境强制限制（不可绕过）
2. 本文件定义的人工门禁、授权边界与 Definition of Done；以及任务中**已批准**的执行授权包
3. 用户即时口头指令：若改变目标、范围、验收或交付级别，必须回到 `drafting` 更新授权包并重新确认；不得解释为「可以跳过门禁」
4. `.agent-workflow/PROJECT.md` 与当前任务设计
5. 宿主适配文件（Codex 的 `AGENTS.md` / Cursor Rules / `.starFactory/` 等）

适配层只能填充 `CAPABILITIES.md` 中的实现格子，不能改写本文件的阶段与完成标准。Claude Code 不在当前使用宿主之列，其材料仅作设计参考，见 `docs/reference/claude/`。

## 2. 基础状态

| 状态                 | 含义                       | 允许的下一状态                            |
| -------------------- | -------------------------- | ----------------------------------------- |
| `drafting`           | 探索、规划和设计           | `awaiting_approval`, `blocked`            |
| `awaiting_approval`  | 等待人工确认执行授权包     | `approved`, `drafting`, `blocked`         |
| `approved`           | 授权基线已经确认           | `implementing`, `blocked`                 |
| `implementing`       | 在授权范围内修改           | `validating`, `blocked`                   |
| `validating`         | 执行真实验证               | `reviewing`, `implementing`, `blocked`    |
| `reviewing`          | 独立、只读 Review          | `fixing`, `ready_for_delivery`, `blocked` |
| `fixing`             | 修复 Review 或最终检查问题 | `validating`, `blocked`                   |
| `ready_for_delivery` | 执行 DoD 和交付检查        | `fixing`, `done`, `blocked`               |
| `done`               | 已按授权级别完成交付       | 终态                                      |
| `blocked`            | 需要人工决策或外部条件变化 | 恢复到被阻断前状态或终止                  |

禁止跳过 `awaiting_approval → approved` 门禁。Fast Path 可以简化规划和设计内容，但不能跳过人工确认。

## 3. 路径选择

### Fast Path

仅当下列条件全部成立时使用：

- 目标和预期行为明确。
- 影响范围局部且可快速回滚。
- 不改变公共接口、数据语义、权限、依赖或关键配置。
- 不需要数据库迁移或生产操作。
- 回归范围清晰。

### Standard Path

默认路径。适用于功能、非琐碎 Bug、行为变化和局部重构。

### Governed Path

满足任意一项即升级：

- 认证、授权、隐私或敏感数据。
- 数据库 schema、数据迁移或不可逆写入。
- 基础设施、生产环境或关键运行配置。
- 依赖升级可能产生兼容性或供应链风险。
- 公共 API、协议、配置格式或持久化数据变化。
- 故障可能导致安全事件、数据丢失或大范围不可用。

无法确定时采用风险更高的路径。

## 4. 阶段 A：探索、规划和设计

### 4.1 先探索，后提问

执行者必须先读取真实代码、配置、测试和版本控制状态。可以从项目发现的事实不得反问用户。

探索结果至少记录：

- 相关入口、模块和测试。
- 当前行为和问题证据。
- 可复用的现有模式。
- 工作区已有变更及冲突风险。
- 尚未验证的假设。

### 4.2 执行授权包

规划与设计必须包含：

- 目标、非目标和验收条件。
- 影响文件、接口、数据和外部系统。
- 推荐方案及主要取舍。
- 错误、边界、兼容和回滚处理。
- 测试与验证方案。
- 路径分类和 Review Profile。
- 高风险操作及确认要求。
- 交付级别，默认 L2。

### 4.3 人工确认门禁

进入 `awaiting_approval` 后停止变异操作。人工明确批准执行授权包后：

1. 在任务文件记录批准时间、批准内容和交付级别。
2. 将状态更新为 `approved`。
3. 冻结目标、范围、接口契约、验收条件和风险等级。
4. 开始自主执行，不再因普通技术选择等待人工。

人工要求修改时回到 `drafting`，更新授权包后重新确认。

## 5. 阶段 B：AI 自主执行

### 5.1 实现

- 遵循现有架构和项目规范。
- 优先最短逻辑路径和最小影响范围。
- 保留用户已有变更，不清理无关内容。
- 为行为变化增加或更新测试。
- 对异常路径提供明确错误处理。
- 实现过程中记录与设计不同但不改变基线的内部决策。

### 5.2 验证

按 `PROJECT.md` 中声明的命令执行：

1. 优先运行 touched-scope 测试、Lint 或类型检查。
2. 修复局部失败后运行相关回归。
3. 进入交付前运行项目要求的完整验证。
4. 记录命令、退出结果、关键输出和未运行原因。

检查失败时回到 `implementing` 或 `fixing`，不能以环境推测替代真实排查。

### 5.3 独立 Review

Review 只读执行，优先级如下（具体宿主工具见 `CAPABILITIES.md` 的 `review` 行）：

1. 独立 Reviewer Agent。
2. 新上下文或新会话 Reviewer。
3. 同一执行者按 `REVIEW_TEMPLATE.md` 串行复审。

Review 必须核对真实 diff、任务验收条件和验证证据。每条 Finding 必须包含位置、影响、证据、优先级和置信度。不得引入 Claude Code 或其它非当前宿主的专属插件来完成 Review。

### 5.4 修复与复验

- P0、P1 必须修复并复验。
- P2 必须修复或记录接受理由。
- P3 可记录为后续建议。
- 修复后重新运行受影响验证，并重新检查原 Finding。
- 自动循环最多 3 轮；超过上限进入 `blocked`。

## 6. 人工介入条件

除以下情况外，执行者不得暂停自主流程：

- 需要改变已批准的目标、范围、验收条件或公共契约。
- 需要执行 `PROJECT.md` 未授权的高风险或外部操作。
- 缺少凭证、环境、数据或外部权限。
- 发现严重安全、隐私、数据丢失或生产事故风险。
- 项目真实状态推翻执行授权包的关键假设。
- 同一阻断问题完成 3 轮修复仍未解决。

进入 `blocked` 时必须提交：

- 精确阻断条件。
- 已完成的检查和尝试。
- 关键日志或错误证据。
- 2 至 3 个互斥选项及推荐项。
- 每个选项对范围、风险和交付的影响。

## 7. 交付级别

| 级别 | 允许操作                         |
| ---- | -------------------------------- |
| L1   | 本地修改和验证                   |
| L2   | L1 + 原子 Git Commit             |
| L3   | L2 + 推送功能分支和创建或更新 PR |
| L4   | L3 + 合并或部署                  |

默认 L2。L3、L4 必须在执行授权包中逐次明确。任何级别都不能绕过宿主环境的安全审批。

## 8. Definition of Done

进入 `done` 前必须全部满足：

- [ ] 所有验收条件有通过证据。
- [ ] 实际修改未超出批准范围。
- [ ] 项目要求的验证命令已运行并记录结果。
- [ ] 未运行项目及原因已披露。
- [ ] P0/P1 为零。
- [ ] 修复项已完成相关复验。
- [ ] P2 已处理或明确接受。
- [ ] 遗留风险和后续事项已记录。
- [ ] Git 状态与批准的交付级别一致。
- [ ] 最终交付报告完整。

如果任何项目未满足，状态只能是 `ready_for_delivery`、`fixing` 或 `blocked`，不能是 `done`。

## 9. 最终交付格式

```markdown
## 实现结果

## 修改清单

## 验收结果

## 验证证据

## Review 与修复

## 遗留风险

## Git 与交付状态
```

最终交付必须区分：已验证事实、未执行检查、推断和遗留风险。

## 10. 跨 Agent 接力

换 Agent 或恢复会话时，新执行者必须：

1. 读取启动顺序中的文件。
2. 检查工作区和版本控制真实状态。
3. 对照任务文件确认当前状态和最后一条证据。
4. 不重复已经有可靠证据的工作。
5. 对无法验证的历史结论标记为“待复验”。
6. 从当前状态允许的下一步继续。

## 11. 经验沉淀

每个任务结束时记录本次踩坑、误报、遗漏和有效模式。晋升规则：

- 安全或破坏性红线立即进入全局规则。
- 重复行为问题进入规则或 Review 清单。
- 已验证的完整方法进入 Skill。
- 跨项目稳定原则进入本文件。
- 一次性偏好保留在项目或任务级。
